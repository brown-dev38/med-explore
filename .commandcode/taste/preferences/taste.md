# Preferences
- Communicates in Thai; expects the assistant to respond in Thai (even when the conversation carries some English text). Confidence: 0.8
- Wants the app's home page `/` to be the canonical auth landing point: after logout, redirect to `/` rather than back to `/login`. Confidence: 0.6
- Works in phased, sprint-based increments: supplies a numbered plan of Sprints (each with a name, rough time estimate, and scope bullets) and expects the assistant to plan and execute against that order (detailed for the current sprint, overview for later ones). Confidence: 0.62
- Prefers back-office (admin/organizer) areas to be organized as dashboards with a persistent sidebar navigation shared across roles, and prioritizes ease of use over plain pages. Confidence: 0.55
- Expects login to land each role on its own dedicated dashboard section (admin → admin dashboard, organizer → organizer area, student → student dashboard) rather than a generic post-login page or plain public route. Confidence: 0.7
- Wants each dashboard section to be self-contained: sidebar items/links must stay within that section's own paths (no links that jump into another role's section) and irrelevant shortcuts (e.g. "back to home", "scan QR" for admin) should be omitted. Confidence: 0.62
- Expects in-dashboard destinations (profile, activities list/detail) to render inside the dashboard's content area under the shared shell as nested paths of the section (e.g. `/dashboard/activities`, `/dashboard/my-activities`), not navigate out to standalone public routes — he will push back with a terse "why isn't it /dashboard/activities?" if a page stays on a top-level public URL. Confidence: 0.75
- When reporting a bug he also asks the cause ("ทำไมแสดง...?"), so he expects a root-cause explanation of the symptom alongside the fix, not just a silent code change. Confidence: 0.5
- Requests features in terse, telegraphic Thai bullets and expects the assistant to fill in the concrete UX details (countdown display, auto-expiry behavior, permission checks, fallback/manual input) and to report what was verified. Confidence: 0.65
- Expects back-office roles (ADMIN/ORGANIZER) to have manual override over student flows — e.g. adding participants on a student's behalf (even for un-PUBLISHED/draft activities) and creating or editing check-in/check-out times — rather than only students being able to register/check in themselves. Confidence: 0.5
- Wants dashboard/summary sections to show a bounded preview with a "view all" link to a dedicated full-list page (e.g. dashboard shows only the 4 nearest upcoming activities plus a link to an "upcoming activities" page), rather than listing everything inline. Confidence: 0.5
- Wants to be able to verify flows himself in local dev and asks how to test end-to-end on a computer (without special hardware like a phone); expects the assistant to make flows readily testable and to spell out the concrete test steps. Confidence: 0.5
- Tests the app himself on a real phone over the LAN (e.g. via an IP like 192.168.1.49), and reports bugs from that setup — so dev-mode access through non-localhost origins (login, QR/scan flows) must actually work, not just on localhost. Confidence: 0.65
- Expects any absolute URL the server generates (QR-code links, redirects) to be derived from the host the user actually opened the app through (request Host/forwarded headers), not from a hardcoded or internal `localhost` origin, so links are usable from other devices on the LAN. Confidence: 0.5
- Reports problems by pasting the exact on-screen/UI error text verbatim (often with no extra context or screenshot description), expecting the assistant to identify the cause and fix it from that string alone. Confidence: 0.6
- Expects test/e2e runs against the real dev database to be non-destructive: he flagged that running tests flipped his real academic year to CLOSED (because temp test data got activated), so testing must avoid mutating global/shared state (activate a temp record via its id instead of switching the singleton ACTIVE row) and restore anything it did change. Confidence: 0.6
- Prefers bulk/batch UI affordances over one-at-a-time actions: asks for multi-select dropdowns, a "select all" option, and applying a change to everyone at once (e.g. set check-in/check-out times for all participants in a single action) — he will explicitly ask to "make it harder" by adding these. Confidence: 0.5
- Prefers solutions that work across all browsers/devices — including iOS Safari — over approaches limited to one browser, and is willing to add a dependency to get that coverage. Confidence: 0.45
- Wants the built system documented as markdown files in a project `docs/` folder (a multi-file set — README/index plus topic files like architecture, database, API reference, features, operations), written in Thai and grounded in the actual code/schema rather than aspirational. Confidence: 0.5
